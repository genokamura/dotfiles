# エンジニアリング共通規律（eng-core）

ミッションクリティカルな開発で LLM（特にミドルクラスモデル）を使う際の規律。
**判断より仕組みを信頼する**: 記憶より状態ファイル、感想より実行結果、
「良さそう」よりチェックリスト。

## 1. 状態の外部化（最重要）

- プロジェクトの状態は**必ずファイルに置く**（PROJECT_STATUS.md / SPRINT.md /
  タスクリスト等）。状態のソースは常にファイルであり、会話の記憶は参考情報にとどめる。
- 作業を始める前に必ず状態ファイルと関連ドキュメントを**読み直し**、
  いま読んだ内容に基づいて作業する。
- 作業単位が終わるたびに状態ファイルを更新する（中断されても他のセッションが
  引き継げる粒度で）。

## 2. 作業単位の規律（small batches）

- 1コミット = 1関心事。目安: 差分 300 行以内。超えそうなら分割を提案する。
- タスクは「1回の red-green-refactor で終わる」粒度まで分解してから着手する。
- 非自明なタスク（複数ファイル・設計判断を含む）は、**実装前に計画を提示して
  合意を得る**。大きな差分は合意済みの計画に沿ってのみ作る。
- リファクタリングと機能追加は別々のコミットに分ける。

## 3. テスト駆動（TDD）

実装タスクは原則この順で進める:

1. **テストリスト**: 対象の振る舞いを箇条書きにする（正常系・境界・異常系）
2. **Red**: 1項目ぶんの失敗するテストを書き、**実行して失敗を確認**する
3. **Green**: テストを通す最小の実装を書き、**実行して成功を確認**する
4. **Refactor**: テストが通る状態を保ったまま整理する
5. テストリストの次の項目へ

- テスト結果の報告は、**実際に実行した出力のみ**を根拠にする。
- バグ修正は**再現テストを先に書き**、失敗を確認してから修正に入る。
- テスト設計の詳細（古典学派の検証規律・モック境界・ピラミッド配分）と
  パイプライン設計は **tdd-cicd スキル**に従う。

## 4. 検証ゲート

コミット・PR の前に必ず以下を実行し、**すべて通ってから**先へ進む:

- [ ] テストスイート（新規・既存とも）
- [ ] リンター / フォーマッタ
- [ ] 型チェック（該当言語）
- [ ] ビルド（該当プロジェクト）

ゲートが未整備のリポジトリでは、最初の実装タスクの前に整備を提案する。
CI がある場合、ローカルゲートは CI と同じコマンドに揃える。

## 5. 誠実性ルール（不変条件）

どの状況でも変わらない、成果の正しさを支える原則:

- 失敗するテストは、**対象コードの実挙動を正すことで**通す。テスト側が
  間違っていると判断した場合は、根拠を示してユーザーの合意を得てから直す。
- テストは**本物の実装**で通す。ハードコードや偽装で緑になった状態は
  「未完了」として扱い、そのように報告する。
- エラー・失敗・未完了は**原文（該当部分）を引用してそのまま報告する**。
  成果報告には、できたことと同じ場所に、できなかったこと・スキップした
  ことを明記する。
- 「存在しない」「実装されていない」と報告する前に、**2つ以上の独立した方法で確認する**
  （大文字小文字を含む検索・別名・呼び出し元の追跡・実際に動かす、のうち2つ以上）。
- 完了・反映の判断は、**管理画面の表示ではなく成果物の実体で行う**。

## 6. 設計判断と ADR

- 後から覆すコストが高い判断（技術選定、データモデル、外部 I/F、認証方式など）は
  `docs/adr/NNNN-タイトル.md` に ADR として記録する（テンプレ: templates/adr.md）。
- ADR は「決定」だけでなく「捨てた選択肢と理由」を必ず書く。
- 迷ったら可逆な選択肢を優先する（feature flag、抽象化の一枚、小さく出す）。

## 7. セキュリティ基準

コードを書く・レビューするとき、常に:

- 秘密情報（鍵・トークン・パスワード）は環境変数・シークレット管理からのみ
  取得し、コード・ログ・コミットの外に保つ
- 外部入力はすべて検証する（境界での型・範囲・サイズ・エンコーディング）
- SQL/コマンド/パス等の組み立てはパラメタライズ・エスケープ機構を使う
- 認証・認可・決済・個人情報に触れる変更では checklists/security.md を実施する
- 依存の追加は「本当に必要か・メンテされているか・権限は最小か」を確認する

## 8. 完了の定義と自己レビュー

「完了」を宣言する前に checklists/preflight.md を実施する。要点:

- 検証ゲート全通過（実行結果に基づく）
- 差分の自己レビュー（`git diff` を読み直す。消し忘れ・デバッグ残骸・
  無関係な変更・コメントの嘘を探す）
- ドキュメント・状態ファイルの更新
- 破壊的変更・マイグレーションにはロールバック手順がある

## 9. 停止点（ユーザーに確認してから進む場面）

- 承認済みの仕様・設計と実装が矛盾すると気づいたとき
- テストや既存コードの「間違い」を直したくなったとき
- 破壊的操作（データ削除、force push、本番系への操作）
- 想定より差分が大きく膨らんだとき（計画とのズレ）
- セキュリティ上の懸念を見つけたとき（まず報告し、対応はユーザーの判断に従う）
