# 古典学派 TDD × CI/CD ハーネス

TDD の実行ループ（red→green→refactor）と検証ゲートの基本は **eng-core** に
従う。このスキルはその詳細規律 — 何をどう検証するか（テスト設計）と、
それをどう自動化するか（パイプライン設計）— を定める。
プロジェクトごとの決定は `docs/TEST_STRATEGY.md`（テンプレートあり）に
外部化し、それを唯一の正とする。

## 1. 古典学派の検証規律

**状態で検証する。相互作用で検証しない。**

- アサーションは**出力と状態**に対して行う。「このメソッドがこの引数で
  呼ばれたか」の検証（interaction verification）は原則禁止。
  リファクタリングでテストが壊れるなら、それは実装に結合したテストである。
- **Sociable unit test を既定とする**: ユニットテストの「ユニット」は
  振る舞いの単位であり、クラス1個ではない。協力オブジェクトは実物を使う。
- **テストダブルは境界にのみ**許可する。境界とは:
  外部ネットワーク（API・外部サービス）/ 時刻 / 乱数 / 環境変数 /
  プロセス外リソース（本物が遅い・不安定な場合のみ）。
  境界の一覧はプロジェクトの TEST_STRATEGY.md に明記し、増やすときは理由を書く。
- ダブルの選好順: **fake（インメモリ実装）> stub（間接入力の固定）> mock
  （相互作用の検証）**。mock は「その相互作用自体が契約」の場合
  （例: 外部への通知送信）に限り、可能なら fake で観測可能な結果に置き換える。
- **自分が所有しない型をモックしない**: サードパーティはラッパーで包み、
  ラッパーの向こう側だけをダブルにする。

## 2. テスト設計

- **受入基準がテストの源泉**: PBI / 要件の Given/When/Then を、そのまま
  テストリスト（正常系・境界・異常系）に変換する。テスト名は振る舞いの
  仕様として読めること（`test_1` や `works correctly` を禁止）。
- **構造は AAA**（Arrange / Act / Assert）。1テスト1振る舞い。
  Assert が複数あってよいのは同一振る舞いの複数側面のとき。
- **テストピラミッド**で層を配分する:

| レベル | 内容 | 実物/代役 | 速度目標 |
|--------|------|----------|---------|
| unit（大多数） | sociable なユニットテスト | 境界以外すべて実物 | スイート全体で秒〜分 |
| integration（一部） | 実インフラとの結合（DB・キュー等はコンテナで実物） | 外部 SaaS のみ代役 | 分単位 |
| E2E（少数） | 主要ユーザーシナリオの薄いスモーク | 全部実物 | 本数を絞る |

- **非決定性の排除**: sleep 待ち・実時刻・実乱数・テスト間の順序依存・
  共有可変状態を禁止。時刻と乱数は境界として注入する。
- **レガシーコードは characterization test から**: 変更前に現状の振る舞いを
  固定するテスト（golden master 含む）を書き、その保護下でリファクタする。
- カバレッジは**下限のラチェット**として使う（後述）。数字を目的化しない —
  アサーションのないテストでカバレッジを稼ぐことを禁止する。

## 3. パイプライン設計（CI/CD）

- **ローカル = CI パリティ**: 検証はすべて単一のコマンド群（Makefile /
  package.json scripts 等）に定義し、開発者も CI も**同じコマンド**を叩く。
  CI にだけ存在する検証ロジックを禁止する（eng-core §4 の具体化）。
- **フィードバック速度でステージを分割**し、安いものから先に落とす:

| ステージ | 内容 | 目標時間 | 失敗時 |
|---------|------|---------|--------|
| commit | lint・型・unit | < 10分 | 即修正（最優先の割り込み） |
| integration | 結合テスト（コンテナで実物） | < 30分 | 同上 |
| e2e / nightly | E2E スモーク・重い検査 | 定期実行可 | 翌朝までに triage |

- **トランクベース**: 短命ブランチ・小さな PR（eng-core の作業単位と同一）。
  未完成の機能はフィーチャーフラグで隠して main に入れる。
  **main は常にデプロイ可能** — 壊れたら全員の最優先事項は修復。
- **ビルドは1回、昇格はアーティファクト**: 環境ごとに再ビルドしない。
  同一アーティファクトに環境設定を注入して昇格させる。
- **ラチェット**: 品質ゲート（カバレッジ下限・lint ルール・型の厳格度）は
  締める方向にのみ自動で動かす。緩める変更は人間の承認と記録
  （PROJECT_STATUS / SPRINT の例外記録）を必須とする。
- **フレークは欠陥**: 不安定なテストを retry で握りつぶす設定を恒久策に
  しない（eng-core 誠実性ルールの適用）。検出したら隔離（quarantine）し、
  Issue 化して期限を付け、TEST_STRATEGY.md の隔離リストに載せる。
  qa-verifier / オーケストレーターはフレーク判定を Opus で裁定してよい
  （scrum/agent-team.md モデルポリシー）。
- **パイプラインもコード**: ワークフロー定義はレビュー対象。秘密情報は
  CI のシークレットストアのみ（リポジトリに置かない — eng-core §7）。
- **ロールバック可能性**: デプロイには検証済みの戻し手順を用意する。
  DB マイグレーションは expand–contract（後方互換な2段階）で書く。

## 4. エージェント実行との接続

- `/tdd` での実装時、モック方針は本スキル §1 に従う。テストリストは
  `/test-design` の成果物（または受入基準）から作る。
- dev-reviewer は §1・§2 違反（実装結合・境界外モック・非決定性）を
  レビュー観点に含める。
- preflight・DoD の「検証ゲート」は TEST_STRATEGY.md のコマンド表を指す。

## テンプレート

- templates/TEST_STRATEGY.md — プロジェクトのテスト戦略書（境界一覧・
  コマンド表・ラチェット・隔離リスト）
- templates/github-actions-ci.yml — ステージ分割済みの CI 雛形
