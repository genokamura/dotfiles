# エージェントチーム実行プロトコル（/sprint-run が参照）

少数の人間（PO）と複数の開発エージェントでスプリントを実行するための調停規約。

## 役割

| 役割 | 担当 | やること / やらないこと |
|------|------|------------------------|
| PO | 人間 | 決定クラス（下記）の判断のみ。実装・レビューはしない |
| オーケストレーター | メインセッション | 分解・割当・調停・統合・エスカレーション。**自分では実装しない** |
| dev-implementer | サブエージェント | 割当タスクの TDD 実装（並列時は worktree 分離） |
| dev-reviewer | サブエージェント | 差分の敵対的レビュー（読み取り専用） |
| qa-verifier | サブエージェント | ゲート・受入基準の実行検証（読み取り専用） |

## 人間の決定クラス（これ以外は自動で進める）

1. **ゴール/スコープ**: スプリントゴール、PBI の入替・追加・削除
2. **受入**: スプリントレビューでの PBI 受入判定
3. **設計**: ADR に相当する不可逆な判断の承認
4. **裁定**: 実装とレビューの意見対立（差し戻し2回超）、blocked の解消方針
5. **リスク**: 破壊的操作・セキュリティ懸念・本番影響のある操作の承認

エスカレーション時は「状況 / 選択肢 / 推奨」を1画面に収めて提示し、PO の
判断を待つ。判断待ちの間、依存しない他タスクの処理は継続してよい。

## 状態はボードがすべて

- SPRINT.md のタスクボードが唯一の正。エージェントの割当・状態遷移は
  **ディスパッチ前に**ボードへ書き込む（クラッシュしても再開できるように）。
- サブエージェントは会話を共有しない。必要な文脈（タスク定義・受入基準・
  対象ファイル・規約）はすべてプロンプトで明示的に渡すか、読むべき
  ファイルパスを指定する。
- タスク状態: `未着手 → 実装中 → レビュー中 → 検証中 → 統合済み → 受入待ち`
  ＋ `ブロック`（どの状態からも遷移可）

## ディスパッチ・プロンプト規約（コンテキストパケット）

ワーカーは Sonnet 級モデル。公式プロンプティングガイドの知見に基づき、
ディスパッチ時のプロンプトは以下を守る。

**原則**（Sonnet 系の特性への対応）:

1. **全量を最初の1ターンで**: タスク仕様・意図・制約を最初に完全に渡す。
   逐次の小出し・「まず着手して、詳細は後で」はトークン効率と性能を下げる。
2. **字義通りに解釈される前提で書く**: 適用範囲を明示する（「全セクションに
   適用」「このファイルのみ」）。暗黙の一般化は起きない。「適切に」「必要に
   応じて」のような判断基準のない語は、基準を添えるか削る。
3. **意図（why）を渡す**: 何のための作業か（PBI・スプリントゴールとの関係）を
   1〜2文添える。目的が分かると文脈への接続が正確になる。
4. **使用条件を明示**: ツール・能力は「いつ使うか」まで書く（「テスト実行には
   `npm test` を使う」「不明点があれば推測せず blocked で返す」）。
5. **本文で自己完結させる**: サブエージェントは会話を共有しないため、
   必要な情報はすべて本文に書くか、読むべきファイルパスで渡す
   （「前述の通り」「さっきの方針で」は届かない）。

**パケット構造**（この形でプロンプトを組み立てる）:

```
<task>
タスクID・内容・完了条件（対応する受入基準を原文で引用）
</task>
<why>
この作業の目的。どの PBI / スプリントゴールに寄与するか
</why>
<scope>
変更してよいファイル・領域 / 現状のまま保つもの
</scope>
<inputs>
読むべきファイル（SPRINT.md、関連設計、~/.claude/skills/eng-core/SKILL.md 等のパス）
</inputs>
<constraints>
検証コマンド（テスト・リント・型）、コミット規約、期限や差分サイズの目安
</constraints>
<output>
期待する報告形式（各エージェント定義の形式を再掲 or 参照）
</output>
```

## タスクパイプライン

各タスクについて:

1. **dispatch**: dev-implementer に割当（上記コンテキストパケット規約に
   従ったプロンプトで。タスク定義・受入基準・読むべきファイルを全量明記）
2. **review**: 完了報告を受けたら dev-reviewer に差分レビューを依頼
   - reviewer は coverage-first（全指摘 + severity/confidence 付き）で返す。
     フィルタリングはオーケストレーターの責務
   - request_changes → 指摘を添えて dev-implementer に差し戻し（**最大2回**。
     超えたら人間へ裁定エスカレーション）
   - approve に confidence: low の指摘が残っている場合、それらを verify の
     ディスパッチに含め、qa-verifier に実挙動で白黒を付けさせる
   - reject（テスト改竄等）→ 即エスカレーション
3. **verify**: approve 後、qa-verifier がゲート・受入基準を実行検証
   - fail → 差し戻し（review と同じ上限）
4. **integrate**: オーケストレーターが統合（worktree のマージ等）。
   コンフリクトは機械的に解決できる場合のみ自力で、設計判断を伴うなら
   エスカレーション
5. ボードを更新し、次のタスクへ

## 並列実行の規律

- **依存関係のないタスクのみ**並列にディスパッチする（ボードの depends 列で判定）
- 並列の実装エージェントは**必ず worktree 分離**で起動し、1つの作業ツリーは
  常に1エージェントが占有する
- 同一ファイル群に触れそうなタスクは、依存がなくても直列化する
  （タスク定義の対象ファイルから予測。外れてコンフリクトしたら統合時に処理）
- 同時実行数は控えめに（目安 2〜3）。レビュー・検証はタスクごとに独立なので
  パイプライン化してよい（タスクAのレビュー中にタスクBの実装を進める）

## モデル選択ポリシー（コスト最適化）

モデル階層の使い分け。価格比の目安: Opus ≈ Sonnet の 1.7倍/トークン、
Haiku ≈ Sonnet の 1/3。エージェント定義の既定は Sonnet で、オーケストレーターが
ディスパッチ時に以下の表に従って上書きする（Agent 呼び出しの model 指定）。

| 役割・状況 | モデル | 根拠 |
|-----------|--------|------|
| オーケストレーター | セッションのモデルに固定 | 分解・調停・統合は判断の集約点。**会話途中のモデル切替はキャッシュを無効化する**ため固定し、安いモデルはワーカー側で使う |
| 実装（通常タスク） | Sonnet | コーディング/エージェント作業で Opus 級品質、コスト約6割 |
| 実装（機械的な小タスク: 定型変更・rename・boilerplate・ドキュメント） | Haiku 可 | 1/3 コスト。200K context 上限に注意（大きなリポジトリの横断作業には使わない） |
| 実装（critical PBI / 複数ファイル横断の大規模変更 / 長時間自律） | **Opus** | 長期整合性と一発完成率が高い。手戻り（差し戻し×往復コスト）込みの総コストでは安くなることが多い |
| レビュー（通常） | Sonnet | coverage-first + 下流フィルタで補強済み |
| レビュー（critical PBI の2体目） | **Opus** | 実バグ検出力が最も高い。レビューは読む量に対し出力が短く、Opus 化のコスト増が小さい＝品質投資のレバレッジ最大点 |
| 検証（qa-verifier） | Sonnet | 実行と結果報告が主体 |
| フレーク（不安定テスト）の切り分け | **Opus** | 「1回通ったから修正済み」と誤判定しにくい。sonnet の判定が揺れたら Opus で再検証 |

**昇格の記録**: Opus を使ったディスパッチは、ボードの担当/メモ列に
`impl:opus(理由)` の形で理由込みで記録する。レトロで配分の適否を検証する
（過剰昇格＝コスト浪費、過小昇格＝差し戻し多発、の両方を見る）。

**Opus リトライ**: 差し戻し上限（2回）に達したタスクは、人間へ裁定を仰ぐ前に
**Opus の実装エージェントで1回だけ**リトライしてよい（ボードに記録）。
それでも解決しなければ人間へ。これにより人間の割り込みを本当に判断が必要な
案件に絞る。

**effort の目安**（設定可能な環境では）: 機械的タスクは low、通常実装は
既定、レビュー・検証・critical 実装は high。

## 品質の非対称性ルール

実装より検証を厚くする（ミドルクラスモデルの並列実行では、生成の速さより
誤りの検出が律速）:

- レビューと検証は**実装と別エージェント**で行う（自己レビューで代替しない)
- critical な PBI（認証・決済・データ破壊の可能性）はレビューを2体
  独立で走らせ、指摘の和集合を採用する（うち1体は Opus — モデル選択
  ポリシー参照）
- ゲートの失敗は原因を特定してから扱う。再実行はフレーク切り分けの手段として
  qa-verifier が行い、その判定結果に基づいて次の行動を決める

## 進捗の可視化

- 各タスクの状態遷移時に1行のログ（タスクID・新状態・担当）を PO 向けに出す
- スプリント全体の残タスクとブロッカーは、いつでも /standup で確認できる
  状態を保つ（＝ボードを常に最新に）
