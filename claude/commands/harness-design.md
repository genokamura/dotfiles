description: 開発プロセスハーネス（Skill / Command / Agent）の設計・拡張を、確立済みの設計原則と手順で再現性高く実行する
---

あなたはこれから、Claude Code 用の開発プロセスハーネス
（dotfiles の `claude/` 配下 = ~/.claude/ にリンクされる Skills / Commands /
Agents / templates）を設計・実装します。以下の手順と設計原則に**必ず**従うこと。

対象テーマ: $ARGUMENTS
（未指定なら「何のプロセス・規律をハーネス化したいか」をまず確認する）

## 手順

1. **要求の明確化**: 目的・利用シーン・人間の関与度（どの判断を人間に残すか）を
   確認する。設計の方向を左右する未確定点だけを、選択肢付きで質問する（最大3問。
   慣例で決められることは聞かずに進め、採用した既定を報告に書く）。
2. **最新知見の調査**: モデルの挙動・プロンプティング・コストに依存する設計を
   **記憶で書かない**。claude-api スキル（利用可能なら）や公式ドキュメントで、
   対象モデルの特性・価格比・推奨プラクティスを確認してから設計する。
   調査結果のうち設計判断に使った根拠は、成果報告に要約して残す。
3. **設計の合意**: 下の設計原則チェックリストに照らして、ファイル構成
   （skills/commands/agents/templates）と各ファイルの責務・相互参照を
   1画面で提示し、ユーザーの合意を得てから実装に入る。
4. **実装**: dotfiles リポジトリの `claude/` 配下に作成する。
   - 既存の関連 Skill との関係を必ず張る（共通規律は委譲、重複記述しない）
   - README のハーネス節を更新する
   - 既存ハーネスと矛盾する規律に気づいたら、黙って追加せず統合案を提示する
5. **検証**: 実装後に確認する —
   - frontmatter が閉じている / description が「いつ使うか」を具体的に述べている
   - 本文中の参照パス（テンプレート・スキル・チェックリスト）が実在する
   - 入口 Command が乱立していない（1テーマ3個目安）
   - 誤字・混入文字（コピペ由来の異言語文字等）がない
6. **コミット & プッシュ**: 変更理由（why）が分かるメッセージでコミットし、
   指定ブランチへ push する（main 運用中なら main も更新）。
7. **フィードバックループの明示**: このハーネスをどう検証・改善するか
   （レトロ項目・記録する指標・調整箇所）を成果報告に含める。ハーネスは
   一発で完成しない前提で、運用データが改善に還流する仕掛けを必ず入れる。

## 設計原則チェックリスト

### アーキテクチャ
- [ ] **プロセス知識は Skill、入口は Command（少数）、実行体は Agent** の3層
- [ ] Skill の description は自動読み込み条件を具体的に
      （ファイル存在条件・コマンド名・トリガーとなるキーワード）
- [ ] 成果物ドキュメントには templates/ を用意（{{PROJECT_NAME}}・{{DATE}} 等の
      プレースホルダで統一）
- [ ] ID 体系が要るなら定義する（連番・不変・廃止は記録、参照は `参照:` 行）

### ミドルクラスLLM補償（5原則）
- [ ] **状態の外部化**: 状態は必ずファイル。会話記憶をソースにしない。
      作業開始時の読み直しを強制する
- [ ] **小さな作業単位**: 完了条件が明確な粒度まで分解してから着手
- [ ] **実行結果に基づく検証**: チェック項目は実行コマンドと結果の添付を要求。
      推測チェック禁止
- [ ] **明示的な停止点**: 人間に確認すべき場面を列挙（決定クラスとして最小化）
- [ ] **誠実性ルール**: テスト改竄・偽装・失敗の取り繕いを絶対禁止として明文化

### マルチエージェント（該当する場合）
- [ ] サブエージェントは会話もスキルも継承しない →
      定義冒頭に「最初に読むファイル」を指示する
- [ ] ディスパッチはコンテキストパケット
      （task/why/scope/inputs/constraints/output を**全量・最初の1ターン**で。
      会話参照の禁止、適用範囲の明示 — 字義通り解釈される前提で書く）
- [ ] **職掌分離**: 生成と検証は別エージェント。検証を生成より厚く
- [ ] 並列は worktree 分離。依存と対象ファイルで直列判定。
      ボード（状態ファイル）が唯一の正、割当は**ディスパッチ前に**書き込む
- [ ] レビュー系エージェントは **coverage-first**
      （全件報告 + severity/confidence 付与。フィルタは下流の責務 —
      「確信がなければ報告するな」系の指示は recall を下げるので書かない）

### コスト最適化
- [ ] モデル・ルーティング表を定義（既定 Sonnet / 機械的→Haiku /
      critical・大規模横断・フレーク切り分け→Opus / オーケストレーターは
      セッションモデルに固定 — 途中切替はキャッシュ無効化）
- [ ] 昇格は理由込みでボードに記録 → レトロで配分を検証するループ
- [ ] エスカレーション階段（例: 差し戻し上限 → Opus リトライ1回 → 人間）で
      人間の割り込みを最小化

### 人間の関与
- [ ] 人間の決定クラスを列挙して最小化（例: ゴール/スコープ・受入・ADR級設計・
      裁定・リスク）
- [ ] エスカレーションは「状況 / 選択肢 / 推奨」を1画面で提示
- [ ] Done の判定は人間（エージェントの自己宣言を禁止）

## 禁止事項

- モデル特性・価格を調査せずに記憶で断定すること
- ユーザーの合意（手順3）なしにファイルを大量生成すること
- 既存ハーネスとの矛盾を検出したまま黙って上書きすること
